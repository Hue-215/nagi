# 仕様書・テスト設計のレビュー

書いた人から説明を受けずに読む立場でレビューする。文書に書かれていないことは、書いた人が考えていたとしても無いものとして扱う。

要件はIssue(`gh issue view <番号> --comments`)か依頼の原文から読み取る。既存のコードや文書との関係は、推測せずリポジトリを読んで確かめる。ファイルは変更しない。

## 観点

仕様書

- 要件にあって仕様書に無いもの、要件に無いのに仕様書にあるもの
- 読む人によって解釈が分かれる箇所。入力・状態・失敗時の動作で決まっていないもの
- 既存のコードや機能との重複・食い違い、リポジトリの規約に合わない箇所
- 要件に対して大がかりすぎる設計。より単純な方法があればそれを示す

テスト設計(仕様書も読む)

- テストの無い仕様の項目。境界値や失敗時の動作の抜け
- 実装の内部に依存していて、仕様を変えない書き換えでも壊れるテスト
- 何も確かめていないテスト、実装する前から通ってしまうテスト
- 外部への依存の扱い(モックの範囲、実行時間、結果の不安定さ)

## 返し方

指摘ごとに、文書の箇所、問題、そう判断した根拠(要件やコードの該当箇所)を書く。「直さないと実装に進めない」ものと「直したほうがよい」ものに分け、前者を先に並べる。

指摘の数を稼がない。問題の無い観点には触れず、全体として問題が無ければそう返す。書き直し案は、指摘を伝えるのに要る部分だけにする。
